Engineering report · beadcause

One person, many agents, and the channels between them

Beadcause is a decision inbox: a Mac daemon that turns bd issues into questions on a phone, and gives the agents working those issues a small set of commands for reaching the one human who has to answer. This is how it is built, how work moves through it, and what the agents are allowed to say.

01 · The shape of the thing

The premise, and the rules that follow

A bead reaches the phone because it is asking something. Everything else in beadcause is downstream of that one sentence.

An agent working a repo hits a decision it cannot make — gross or net, which auth flow, is this one bead or four. It files an issue labelled human with a fenced decision block in the body: the question, the options, the exact response text each option records, a mermaid diagram, files to read, links, images. The daemon sweeps every beads workspace under ~/beads/, pushes what is new, and serves a mobile-first PWA over the tailnet. Answering writes a bd comment and closes the bead, so whatever was blocked on the answer turns up in bd ready for the next session.

That loop is old. What has grown around it is everything needed to make it survive many agents running unattended: a repo advocate that cares whether the queue reaches zero, a delivery path where a worker merges its own pull request, a per-agent memory that outlives a run, and a constitutional channel where an agent can ask to be given a tool it was denied.

The invariants

Each of these is enforced by code, not only by a prompt. They are the load-bearing walls — most of the design below is a consequence of one of them.

  • No agent may create a bead. Proposing is as far as it goes; the human taps, and beadcause runs bd create. The chat session's allowlist has no write verb at all.
  • Nothing pushes to main. There is no push in lib/pr.js. The only route into main is a branch, a pull request, and a merge GitHub serialises.
  • A reply agent never closes the bead it is answering. The allowlist names bd subcommands one at a time precisely so close, create, delete and label are absent.
  • Two pollers never exist at once. A duplicate notification is the one thing the blue/green swap must never produce.
  • Nothing binds 0.0.0.0. The router takes loopback and the Tailscale IP; the backends behind it take loopback only.
  • Every state file is replaced, never overwritten — temp file, fsync, rename — and then committed, so its history exists whether or not anyone thought to make a backup.
  • The memory API takes no repo, no path, and no identity. Who an agent is arrives as BEADCAUSE_AGENT in its environment; an agent that could name itself could write into another's memory indistinguishably.
  • A narrowed filter narrows the notifications too. The filter lives on the server, so the poller reads the same value the list is drawn from.

02 · Deployment

Processes and topology

What launchd runs is bin/router.js, which owns port 4318 and proxies to a backend on an ephemeral loopback port. The backend is the whole application: HTTP API, static PWA, poller, advocates, dispatcher, pty registry. Everything it touches outside itself is either the tracker, a git ref, a spawned claude, or a push.

Two facts about that picture do real work. The tracker is embedded Dolt and a single writer, so every bd call is a process that can lose a lock race and has to retry — which is why submitting an answer shows “Recording your answer…” rather than a dimmed card. And the config directory is a git repo: state files get a history, and three agent-facing features (memory, the blackboard, foundation amendments) ride on refs inside it rather than on any database.

03 · Why you never restart it

The router, and one poller ever

Static files are read from disk per request; server code is read once, at startup. So editing lib/ leaves a healthy process serving today's pages against yesterday's routes, and a path the page plainly asks for returns 404 with nothing looking wrong. “Remember to restart” is not a fix, because forgetting is the bug.

The honest limits: the router cannot replace itself (that means giving up the socket), so changes to bin/router.js, lib/build.js or lib/config.js need a manual launchctl kickstart, and it says so in the log. A build that will not become healthy is tried once and not retried until the files move again. Every proxied response carries x-beadcause-build and x-beadcause-pid, so curl -sI settles which code actually answered.

npm run swap:status   # active pid, build, whether disk has moved past it
npm run swap          # swap now, even if nothing changed
curl -sI http://127.0.0.1:4318/api/health | grep beadcause

04 · The core loop

The question lifecycle

Everything an agent wants from a human, and everything a human sends back, moves along this one path. The two branches at the end are the whole of the interaction model: answer and close ends the question, comment only starts a thread and dispatches an agent to continue it.

The three counts, and what a sweep costs

/api/questions carries a summary of {sessions, proposals, questions} because the inbox chrome shows those whenever it is on screen — and none of the three costs a bd call. sessions is a readdir of ~/.claude/sessions; proposals counts advocates waiting on an answer, not beads, because one open ask per advocate is the rule; questions is held from the last human sweep rather than counted out of the response, so switching to the agent scope cannot empty it and read as “answered”.

Two channels, split once, server-side

A request to change what an agent is arrives as an ordinary human bead — same decision block, same thread — but never in the work feed. splitChannels hands every surface two lists rather than one list it must filter correctly, and which list a bead is in comes from its label, not from whether its block parsed: a malformed request still arrives in the constitutional channel carrying its error.

Eventsquestion, replyfoundation-request, foundation-reply, amended
Routes/api/questions, /api/poll → questionsthe same two → requests, plus /api/foundation

A request never inherits the bead's priority: work is urgent when it is urgent, an amendment is important and never urgent. The Android channel is the part worth more than it looks — a channel is the unit you control, so constitutional questions can be silenced for a fortnight without touching whether a question about work can reach you.

05 · Definitions

What an agent is

An agent's definition used to be spread across four unrelated places: a system prompt as a template literal, an allowlist as a bare string, a model in a config key, and an environment derived from whichever directory the process happened to be spawned in. That is survivable while the only reader is the code doing the spawning. It stops working the moment an agent is allowed to ask to be different, because you cannot request a change to something with no single form.

So lib/foundation.js: one foundation per agent kind. Read it to know what an agent may do; commit a change to it to change what the agent is. The line it draws matters — a foundation is what the agent is on every run; the prompt handed to one invocation (this bead, this comment, this survey) is what it was asked this time, stays in the module that composes it, and is not amendable. An agent that could rewrite the brief for a task could decide it had been asked something else.

KindJobWritesReachProtocol owner
console the chat session — talks through what should be filed, proposes beads false read-only bd (show list ready blocked search stats comments dep tree), beadcause-memory, Read/Grep/Glob lib/draft.js
dispatch answers a comment left on a question from the phone true — its bd comment is the answer the shared read-only reply allowlist; optionally armed with more for one reply lib/dispatch.js

On top of the four kinds sit the four reply personas a comment can be addressed to — 💬 Answerer, 🔍 Researcher, 🧨 Critic, 📋 Summariser — plus any you define from a name and a paragraph of foundation. They all share the dispatch definition, which is why they also share what dispatch has learned: memory belongs to the thing that has a definition.

Two acts, not one: arming extended tools

Defining reach is a config-file edit and only that — a tools string on an agent entry. Nothing in the app can write it; there is no endpoint that accepts one, because a form on a lock screen is the wrong place to hand out edit rights. Using it is a checkbox that is spent by the comment it rides on: off every time, a warning naming the tools verbatim the first time per agent, refused with a 409 while that agent is answering, printed in full to the log, and visible on the answer box even with the chooser panel shut. The elevated run is also told, in its prompt, that it is elevated for one reply and should say what it did with the reach.

The old allowlist was Bash(bd *) — one pattern and four verbs too many, since it quietly included create, close, delete and label. It is now named subcommand by subcommand, so adding a verb feels like a decision:

Bash(bd show:*) Bash(bd comments:*) Bash(bd comment:*) Bash(bd list:*)
Bash(bd ready:*) Bash(bd blocked:*) Bash(bd search:*) Bash(bd stats:*)
Bash(bd memories:*) Bash(bd dep tree:*) Read Grep Glob

bd dep tree rather than bd dep:* for the same reason: dep is a family, not a read, and the glob one level up carried add, remove, relate, unrelate and the bd dep <id> --blocks <id> shorthand — four graph writes reachable from a comment answered on a lock screen.

06 · The part agents actually touch

The agent comms API

An agent here is a claude in a shell. It has Bash and an allowlist and no way to import anything — so a JavaScript module is a library for the daemon and invisible to the agents it is for. Every channel an agent has is therefore a command.

That constraint shapes the whole surface. Six commands, plus one output convention, plus the bd CLI itself. Each writes into exactly one place, and each has a defined answer to “who notices, and how soon”.

The HTTP equivalents

Everything above has a route, because the phone is a client of the same API. Auth is x-beadcause-token on everything under /api/ except /api/health, or ?t= for URLs that must be linkable — or, for a browser on an install that has configured it, a Google session cookie. The token is asked first either way, so nothing here changes for a caller that has one.

RouteBody / paramsNotes
POST /api/ask{workspace, title, body, priority}files a human bead — and deliberately does not push: you filed it, you are looking at the screen
POST /api/respond{workspace, id, response, create?, edits?}comments, then closes. create is the 1-based indices of a proposal's beads to file; edits is keyed by the same numbers and applied before creating
POST /api/comment{workspace, id, text, agent?}comments, sets human-replied, dispatches that agent
POST /api/status{workspace, id, phase, detail, actor}same as the CLI
GET /api/agent-log?workspace=&id={lines[], running, phase} — the dispatched agent's log, as the CLI would have shown it

POST /api/agent-arm{id, acknowledge?, disarm?}428 the first time carrying the warning, 409 while it is answering, 400 if it has no override

07 · Between runs, and between agents

Memory and the blackboard

A foundation is what an agent is. This is what it has learned — the half that used to evaporate at the end of every run. Six calls, reachable as a command:

beadcause-memory remember tone "evidence first, then the ask"
beadcause-memory recall tone
beadcause-memory note tests "npm test discovers test/*.mjs; scripts/test.mjs is the runner"
beadcause-memory notes tests
beadcause-memory post proposals "the graph work is blocked on a decision"
beadcause-memory read proposals --since=4
beadcause-memory agents
beadcause-memory recall --of=advocate tone

remember/recall are one agent's own knowledge, and it follows the agent into any repo. note/notes are the same two verbs against the repo the command was run in — knowledge about one codebase, which is worth nothing in another. post/read are a blackboard: an agent publishes what it believes and the others read it whenever they next look. Deliberately not a mailbox and not a conversation — no addressee, no delivery, because git has no notification to give. The nudge, where one is needed, is the in-memory event bus, which is the exact complement: payload and durability here, wake-up there.

Which of the two an agent writes to is one question: would this still be true in a different repo? Yes — how Adam likes a thing shaped, an approach that worked anywhere, a dead end not worth walking twice — is remember. No — how this codebase is put together, where its tests live, the trap in one of its files — is note. Neither is an optimisation of the other, and the version with only the cross-repo store is not that minus a feature: its brief said, correctly for it, to write down only what is “still true next week and in a different repo”, which read literally rules out every fact about the code in front of the agent. So knowledge of a codebase either followed the agent somewhere it was false, or was never written at all — and the second is silent.

No call names a repo, a path or a ref, and none of them will take one — not even the pair whose whole subject is a repo. That is the point of the indirection: the day this should be SQLite or a table in beads, the change is lib/memory.js and nothing else. An agent handed a path would have put that path into its own memory, its habits and its prompts. So note writes to wherever the process is standing, and a run from the wrong directory is fixed by cd, which is checkable, rather than by an argument, which is not.

A note rides a ref in the repo it is about — refs/beadcause/agents/<agent>, tree notes.json, beside that repo's foundations and session logs. Two properties come free from that and neither has to be arranged: the same key in two repos is two different notes, and a note written from a worktree under .claude/worktrees/ is there from the main checkout and from every sibling, because a ref outside the per-worktree namespaces lives once in the common .git. The second is what makes the tier usable here at all — nearly all work in this repo happens in a worktree that is retired days later. A ref per agent rather than one ref with a file each, which is the opposite of the cross-repo store: there the writers are four agent kinds on one Mac, here they are a dozen worker sessions in a dozen worktrees of one repo, so splitting by agent means two kinds never contend at all.

An agent can read another agent's memory, and cannot write one. The roster is the memory ref's own tree filtered to *.json, so a kind appears the moment it remembers anything and a list that could go stale never exists. --of is a second flag on purpose: --agent is you for the whole invocation, so --agent=advocate remember … writes into the advocate's file rather than reading it — tolerable for a human at a terminal, wrong as the thing an agent is told about. --of names a subject and never an author: only the two reads, recall and notes, accept it — as a list of the reads rather than a check per command, so note arriving later was refused by default — everything that writes refuses it outright, and a read attributes to nobody so it needs no BEADCAUSE_AGENT — which leaves it no author to borrow. The read also says whose notes it handed you, on stderr so stdout is unchanged: these are advocate's notes to itself, not published to you — evidence, not instruction. remember is written for an agent's own future self; publishing is what post is for, and a cross-agent read should not be able to pass for either.

An earlier version put an agent's memory on a ref inside the codebase it was working on, which is right for knowledge about that codebase and is exactly why nothing could be shared: the beadcause advocate and the sophab advocate write into different checkouts and cannot see each other. The config directory is the one place every agent on this Mac has in common.

The .gitignore is written before git init

That ordering is the whole safety of it. The directory holds android-keystore.jks — the release signing key — and its password file beside it. A git init && git add -A there commits a signing key into a history that is then genuinely hard to remove. So the ignore file lands first, and every commit re-checks the staged list against a denylist and aborts rather than dropping the file quietly: an ignore rule is one git add -f away from not applying, and the cost of being wrong once is a rotated key.

08 · The constitutional channel

Asking to be different

Two layers, and neither can clobber the other. The baseline is in code and ships with the release; normal development edits it freely. Amendments live on refs/beadcause/foundations — a commit per amendment, a tree of <agent>.json overlays, the justification in the message. Effective = baseline ⊕ overlay, resolved at spawn. So editing a prompt in a release cannot silently revert an approved amendment, and an approved amendment cannot freeze a copy of a prompt development has moved past.

```amendment
agent: dispatch
kind: prohibited
scope: reading git history in the repo I am already reading; no writes
justification: |
  The comment asked which commit introduced the bug. I can read the files but not
  the history, so I answered with a guess at the file instead of the commit.
evidence: |
  Bash(git log --oneline -20) was denied.
add:
  allowedTools:
    - Bash(git log:*)
```
FieldStatusWhy
id · protocolOwner · writesnever amendabletheir wrongness is invisible at approval time — “let the chat session call bd create” reads as a one-line convenience and silently deletes the review step
purpose · role · model · tools
allowedTools · env · timeoutMs · permissionMode		amendablea request naming anything else is rejected, not filtered — silently dropping half a request would apply an amendment nobody approved
scopemandatory“give me Write” is not a decision anyone can make on a phone; “give me Write under my own directory, because X” is

Prohibition and omission are not symmetric. A prohibition is observable — the agent asked and was denied, and the denial is in the transcript — so beadcause reads it off the stream rather than taking the agent's word, and puts it on the card under what actually happened. A denial the agent forgot to mention still reaches you; an account of a denial that never happened is catchable. An omission is not observable at all: the agent cannot see what it was never given, so those requests are speculative by construction, and the justification bar is what keeps that half honest.

Commenting on an amendment request re-seeds the requesting agent, not whichever persona you picked from the roster — a Critic explaining why the chat session wants a tool is a stranger guessing at someone else's motive. It is told, in as many words, that withdrawing the request is a better outcome than defending it.

09 · The missing party

Advocates: a queue reaching zero

Everything so far is a channel. A question reaches the phone, an answer reaches the bead, a comment reaches an agent. None of it ever cared whether the work got done — so a repo could sit on nine ready beads for a fortnight and the daemon that knew about all nine would say nothing, because none of them was labelled human and nobody had asked. An advocate is one per repo, interested in nothing except that repo's queue reaching zero.

Advocates are off out of the box. Something that opens Claude sessions on your Mac unprompted should never be a surprise, so the list of repos is empty until you name them. Whenever a cap is what stopped a launch it says so — on the card and in the log — because a slot limit that quietly drops a launch reads exactly like an advocate that decided there was nothing to do.

Why a proposal is n decisions and not one

Flattening a proposal into all-or-nothing is what makes an agent's suggestions annoying: one good bead in three is an ordinary outcome, and having to decline all three to avoid the two bad ones teaches you to decline everything. So the card draws a row per bead — approve, decline, or leave it undecided — with Approve all / Decline all beside an undecided count, and one primary button that says exactly what it will do (“Create 2 of 3”). What was declined is recorded on the closed question alongside what was created, because a proposal answered “create 1 and 3” and closed with only the new ids reads, later, as though 2 was never offered.

Consent is checked against text, because two of the three paths carry only a string: an ntfy action button and a typed answer. CREATE: alone means all of them, CREATE: 1,3 picks by the printed numbers, and the app sends both — the sentence for you, the indices as a field, and the field wins. Free text can never create a bead by accident: “yeah go on then” is a comment, which is exactly what it looks like.

Landing work

What happens to finished work has had three answers, and the third is only defensible because of what the first two taught.

The fallback card, and the two nos that are not the same

The diffstat and check rollup are read from GitHub when the card is drawn, not from the bead: a diffstat frozen at the moment a session ended is wrong the instant anyone pushes, and the one number that has to be right is the one you are looking at when you press merge. The bead carries identity and intent; gh carries state. The check chip has four states because they are four different sentences — 3 checks passing is not no checks, a repo with no CI has told you nothing, and a green tick there would be a claim nobody made.

Request changesDecline
what was wrongsomething on the branchthe approach
the pull requeststays opencloses
the branchstays — push more commits to itabandoned
the beadreopened and unclaimedback in the queue
the next sessioncontinues the same attemptstarts again, fresh branch

Both write your words to both places they are needed — a comment on the pull request, where whoever opens the diff will look, and a comment on the bead, where the next session reads it before starting. Reopening and unclaiming is the part that is easy to miss: a claimed bead never comes back through bd ready, so without it your note would sit on work nothing would ever pick up again. And note which way the markers fail: no wording of a typed answer can merge anything — merging needs MERGE:, and only the button writes it.

The terminal, and why the pty outlives the socket

A phone that locks drops its socket within seconds, and iOS kills it the moment the tab backgrounds. So the pty belongs to the daemon, not to the connection: sockets attach and detach, output accumulates into a scrollback ring while nobody is watching, and coming back replays it into a cleared screen. What ends a terminal is quitting claude, pressing ⏹, or the idle reaper — never a dropped connection.

It survives the daemon too, in the only way that is honest. The terminal picks the session id before the process exists and passes --session-id; a record per terminal is written at lifecycle boundaries only, so the next boot rebuilds the registry with each one marked resumable, holding no process. Attaching is what starts one, with claude --resume. Nothing is spawned at boot — a daemon that respawned four claude processes on startup would be resurrecting sessions nobody asked for — and the scrollback does not come back, because replaying a dead session's bytes into a freshly resumed TUI draws a screen that is half history and half live.

Two details carry more weight than they look. The pty comes from expect(1) and could not have come from script(1), which calls tcgetattr() on its own stdin and only tolerates ENOTTY — a spawned child's stdin is a socket and gives ENOTSUP. And the token rides as a WebSocket subprotocol, never in the URL: a browser cannot set a header on a handshake, and the query string is the one place a secret must not go.

12 · Not losing things

State, durability, history

Everything beadcause remembers between restarts is a small JSON file in the config directory: config.json, state.json (what has been pushed), status.json (what each agent is doing), advocates.json, and one file per chat session and terminal. All of them used to be written with a bare fs.writeFileSync, which truncates to zero and then writes — so a crash, a kill -9, a full disk or a lid closing inside that window did not cost you the last change, it cost the whole file.

Worse, it cost it quietly. Every reader here treats an unparseable state file as an absent one, because that is the right thing to do the first time you run: loadState returns { notified: [] }. So a torn file raises nothing. It just means every question is unread again, every cooldown has reset, and the chat sessions you had open are gone — with nothing in the log saying why.

lib/atomic.js writes to a temp file beside the target, fsyncs it, and renames it over the top. The fsync before the rename is the half that is easy to skip: without it the rename can reach disk ahead of the data it points at, which turns a power cut into a correctly-named empty file — intact-looking, and therefore worse. The temp prompt files handed to claude are deliberately left alone: they are born, read once and deleted, so a torn one is a failed spawn rather than lost state.

That covers a file being torn. What it cannot cover is a file being rewritten with something you did not want — which is why the directory is a git repo and every one of these files is committed after it changes, debounced by two seconds with the reasons accumulating. The config.json.bak-20260808 files that used to sit in there were exactly this feature, performed by hand at moments somebody was nervous.

RefHoldsWhy a ref and not a file
refs/beadcause/memoryone commit per write; tree is <agent>.jsonA ref outside refs/heads/* and refs/tags/* has no working tree, so the daemon can commit one while something else is rewriting config.json beside it — or while you are mid-edit in the repo a note is about — and git status stays clean
refs/beadcause/bus/<topic>one commit per blackboard message
refs/beadcause/agents/<agent>one commit per note; tree is notes.json. In the repo the notes are about, not here — and shared by every worktree of it
refs/beadcause/foundationsa commit per amendment or decline
refs/beadcause/sessions/<bead>an archived session.log, meta.json, optionally the raw transcript

Two caveats worth stating: git log --all does walk refs/*, so these commits appear there and in some GUIs. And nothing is pushed unless you ask — git push origin 'refs/beadcause/*:refs/beadcause/*' is an explicit act, and on a shared repo it should stay one. The second caveat is the one that matters for refs/beadcause/agents/* and refs/beadcause/sessions/*, which live in a repo that has a remote: agent-written text carries absolute paths and whatever tool output scrolled past it.

13 · Blast radius

Security posture

BoundaryHow it is held
NetworkThe router binds 127.0.0.1 and the Tailscale IP, never 0.0.0.0; backends bind loopback only. host falls back to loopback if Tailscale was down when the config was written, which is the failure mode where the phone simply cannot connect.
APIx-beadcause-token on everything under /api/ except /api/health; ?t= only for URLs that must be linkable. The pairing QR carries it once, into localStorage, and it is stripped from the address bar on first load.
A person, in a browserGoogle sign-in beside the token, against an allowlist of addresses (lib/auth.js), off until configured. The token is asked first on every request, so nothing that cannot redirect — an ntfy action button, the Android app, scripts/shot.mjs, the router's proxy hop — ever reaches it. A signed httpOnly cookie is the session; a page requested with no credential is answered with /login, while every asset stays open because none of them holds anything.
Router control/internal/router/* is loopback and token, and never proxied — anyone on the tailnet holding the token could otherwise stop the poller.
WebSocketThe token is a subprotocol, not a query parameter.
Filesystem reads/api/asset and /doc serve only from assetRoots; anything outside is refused.
Agent reachNamed subcommand by subcommand rather than globbed; the advocate's eyes are Bash(node scripts/shot.mjs:*), not Bash(node:*), because writes: false would mean very little standing next to a general node.
ElevationDefining reach is a config-file edit; using it is armed per reply, warned once per agent with the tools named verbatim, refused mid-answer, and printed to the log.
Push privacyAn ntfy topic is readable by anyone who guesses its name, so work questions default to minimal: the notification says only that a decision is waiting. The click URL carries no token. Action buttons are the exception — they must send it as a header — so a full push on a public relay does place the token on ntfy.sh. The Android app posts its own notifications over the tailnet and needs no relay at all.
Secrets at restThe config directory holds the Android release keystore; the .gitignore is written before git init, and every commit re-checks the staged list against a denylist and aborts rather than dropping the file quietly.

Observer mode is not optional for a second instance

BEADCAUSE_CONFIG_DIR isolates the config, the state file and the token. That is all it isolates. The tracker, the repos and .claude/worktrees/ belong to the machine, so a second daemon is a second fully live daemon: its own advocates, its own poll loop, and no idea the first one exists. Booted from a copy of a real config, its first tick opened two Claude sessions in two repos and retired a worktree in the shared checkout. Nothing malfunctioned — it did exactly what the live one does, twice. Boot a second instance with BEADCAUSE_OBSERVE=1: no sessions, proposals, sweeps, session logs, reply agents or pushes.

14 · Evidence

How each claim is kept honest

npm test is pure Node and touches no network, no bead and no repo. The browser-driven checks are deliberately outside it, because they need headless Chrome and, in two cases, a vendored public/vendor.

CheckWhat it proves, and how
test/atomic.mjsSIGKILLs a child writing in a loop and asserts the survivor is always a whole version. --baseline watches the plain writeFileSync it replaced lose the file outright — which is what makes a pass mean anything.
test/memory.mjsRaces six processes onto one topic and asserts the sequence 1..6 is there exactly once. A compare-and-swap you have not raced is one you have not tested.
test/pr.mjsDrives lib/pr.js against a fake gh on PATH, keyed off a world file and a call log — so “it never shelled out” is an assertion. The wait for checks has its sleep injected, so pending-then-green runs in milliseconds.
test/land.mjsCovers the thing with no other interface — the brief, which is all beadcause can make a worker do: that the landing ending never tells a session to merge main by hand, and that the marker line cannot claim CAN BE MERGED over work already in main.
scripts/land-check.mjsThe only place the merge itself runs: real git against a real bare remote, real bd in a scratch workspace, real bin/deliver.js, fake gh. The assertions that matter are negative — gh pr merge must not appear for a red check or --review, and the bead must still be open in every scenario that did not merge.
scripts/shot-check.mjsKeeps the agent's eyes honest, because every way that breaks is silent — a picture always arrives. Fifteen assertions against a fixture page with its own throwaway config, including that the token never reached the output.
scripts/*-check.mjsHeadless Chrome at phone size driving the real public/app.js against fixtures built by the real libraries and parsed back by lib/decision.js — a round trip that never touches a bead. --baseline serves HEAD: versions instead of the working copy, which is how you tell a real failure from a flaky one.
scripts/test-swap.jsDrives a real blue/green swap under load and proves nothing drops.

npm run check is not a test suite, and says so rather than pretending otherwise: it is one file, scripts/check-agent-log.js, the contract the session log rests on. It runs against a throwaway config directory on an ephemeral port and never touches bd, so it is safe with the daemon up.
