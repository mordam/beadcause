# v66 — a bead in the tree expands in place, and the block it expands into has no rules at v65 (bc-rfnr.9.4)

A row in a P0's tree was a link into the graph. It is a `<button>` now, and the tap opens
that bead's own details underneath it: priority, type, owner, every label, what it is under
and what it is behind, the description, acceptance, design, notes and the whole thread.
Two files move together. `public/app.js` gains `p0BeadHtml` and the four renderers under
it, drawing `.p0-bead`, `.p0-bead-meta`, `.pill.lbl`, `.p0-bead-closed`, `.p0-bead-when`,
`.p0-bead-note`, `.p0-bead-acts`, `.p0-rel`, `.p0-rel-group`, `.p0-rel-kind`,
`.p0-rel-row`, `.p0-rel-title` and `.p0-row-caret`; `public/style.css` gains all thirteen,
plus the `button.p0-row` reset that keeps the row looking like the anchor it replaced.

**A v65 stylesheet beside a v66 app.js is the pair that matters, and it is worse than the
usual unstyled block.** Two things go at once.

The first is the reset. `.p0-row` is styled as a link — a bordered, transparent, 12.5px
row indented off `--d` — and at v65 there is no `button.p0-row` rule to strip a button
back to it. So every row in every tree renders as a *browser button*: system font at the
UA's own size, a grey face, a beveled border on all four sides, and — the one that costs
the layout — shrink-to-fit width instead of `width: 100%`, so sixty rows stop being a
column of lines and become sixty buttons of sixty different widths. The tree is still
correct, still in order, still tappable. It simply stops reading as a tree.

The second is the expansion itself. None of the thirteen names above exists at v65, so a
bead you open draws with browser defaults: no indent tying it to its row, no left edge, no
background, the description at the card's own 15.5px — larger than the title of the epic it
is filed under — and the label pills at the shouty upper-case `.pill` size rather than the
9.5px the card scales them to. `.p0-rel-row` loses `flex: 1 1 100%`, so each linked bead
wraps back into its heading's line and `Waits on bc-rfnr.9.1 The server sends the tree`
reads as one sentence rather than as a heading over rows.

Nothing throws and every tap works. That is the point: it looks like a rendering fault in
the section it is drawn in, which is exactly the failure this version number exists to
prevent.

## The number

v66 rather than v62, which is where this branch first put it: [v62](v62.md) went to the
board's status filter (bc-rfnr.9.6), and [v63](v63.md), [v64](v64.md) and [v65](v65.md)
landed behind it — v65 to the advocate switch (bc-04wd) — all four reaching `main` while
this branch was open. The downmerge takes the next free number rather than the one the
branch was written against — a second document under a number `main` has already spent
would make the cache history ambiguous about which shell a given version names, and the
number's only job is to be unambiguous.

v66 is the second time this branch has been renumbered, and the collision was the loud
kind the [README](README.md) asks for: this branch and bc-04wd both wrote a `v65.md`, so
git reported an add/add conflict on one path. The `const` in `public/sw.js` did not
conflict — both sides had set it to the same string — which is exactly why the note is
the file that has to carry the number.

The reverse pair — a v66 stylesheet under a v65 `app.js` — draws nothing at all, because no
v65 page emits any of these classes, and the row is still an anchor that still goes to the
graph. That direction is merely older, which is the direction this repo is happy to leave
alone.
