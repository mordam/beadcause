# v61 — the file that says the app is offline cannot itself be missing offline (bc-lmdv)

`public/freshness.js` is new: every page with a top bar now draws a banner when it has
stopped hearing from the daemon, or when the daemon is answering but has not read the
tracker in a while. It joins SHELL, and adding a file to SHELL is exactly the case the
version exists for — `caches.addAll(SHELL)` runs at **install of a new version**, so a
phone holding v60 would never fetch it. Online that is invisible: the fetch handler is
network-first and the file loads. Offline it is the whole feature missing at the one
moment it was written for, and missing *silently* — a page with no banner is
indistinguishable from a page that is up to date.

That asymmetry is why this is a bump and not an advisory. `test/swbump.mjs` reads the pair
the other way round and calls it merely-older, which it is: v60 HTML has no
`<script src="/freshness.js">`, so nothing draws and the app is what it was. The
direction that fails is the cache never learning about the file at all.

## The other half of the pair

`public/stream.js` and `public/app.js` both stamp `window.beadcause?.fresh?.heard?.()` on
every answer, through an optional chain — so a v60 copy of either beside the new
stylesheet does nothing at all, and a v61 copy beside a v60 `freshness.js` (which does not
exist) is a no-op too. The only mixed pair with a visible effect is a v60 **stylesheet**
under a v61 banner: `.stale` has no rules, so the warning renders as an unstyled line of
text with a button next to it, at the top of the page. Ugly, and still true — which is the
one property a staleness warning has to keep when everything else is broken.

`lib/server.js` puts `sweptAt` and `sweepEverySeconds` on the inbox payload for the second
half of the banner. A cached page that has never heard of those fields draws only the
first half, which is the half that matters.
