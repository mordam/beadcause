# v79 — three notification sounds arrive, and an older stylesheet draws the audition unstyled (bc-ka5y.15.3)

`res/raw` gains `land.wav`, `drop.wav` and `chime.wav` beside the existing `blip.wav`, all
three generated by `scripts/sounds.mjs` and pinned byte-for-byte by `test/sounds.mjs`. The
shell change is the screen they are auditioned on: a new `public/sounds.html` +
`public/sounds.js` at `/sounds`, and the `.sound-*` rules `public/style.css` gains for it.

**Only the stylesheet is in `SHELL`.** `/sounds`, `/sounds.js` and the three `.wav` files
are deliberately left out — see the block beside `/icon.svg` in `public/sw.js` for why. So
the pair that matters here is not the usual one.

**The pair: an older `style.css` under the new page.** The page itself is never cached, so
it always arrives from the daemon and is always current; what a phone can be holding is the
previous stylesheet, which has no `.sound-*` rules at all. The audition then draws as
unstyled blocks — the pads stack, the guess buttons are default-sized `<button>`s, and the
✓ / ✕ the reveal marks answers with are gone with the rules that carry them in `::after`.

That last clause is the only part worth a number. Everything else degrades to
plain-but-usable: every control is still a real button, still labelled in words, still in
the right order. But the reveal's verdict is carried by `.is-right` / `.is-wrong`, and
without the stylesheet a wrong answer and a right one look identical. On a screen whose
entire purpose is telling you whether you named three sounds correctly, that is a page
quietly lying about the one thing it is for.

**The reverse — a new `style.css` on a phone that never opens `/sounds` — is nothing.** The
rules are namespaced `.sound-*` and no other page draws those classes.

## The number

Written against v76, claimed as **v77**, and landing as **v79** — the collision the
[README](../../README.md) asks for, twice over, and both times it happened the way it is
described there. bc-rfnr.9.5 was holding `v77.md` when this note was written and reached
`main` first; bc-khoe.27.1 then took `v78.md` while this branch was still open. Each
downmerge was an add/add conflict on that one path, and each resolved the same way: their
note keeps the number, this one moves up, and the `const` in `public/sw.js` is set by hand
to the highest note in this directory. The pair above is stated against the stylesheet one
version back, because that is the shell a phone will actually be holding.

The number was also, briefly, claimed as v78 *before* any of that — which is worth the
paragraph, because it is the wrong move and it looks like the careful one. Another
worktree was already holding an unmerged `v77.md`, so skipping past it reads as
politeness. It is not: `test/swcache.mjs` requires the notes to be **contiguous**, and a
`v78.md` beside a `v76.md` with nothing between them fails the repo with *no note for v77
— a renumber that skipped, most likely*. The numbers are a property of `main`, not of the
set of worktrees on this Mac, and only `main` can say which of two branches got there
first — which is exactly what it has now said, twice. Arriving at v79 by waiting for the
downmerge is a different fact from guessing a number in advance, and only one of them
leaves the directory contiguous at every commit.

The `const` alone would merge silently — and on the second collision it did exactly that,
both branches having written it `v78` — which is the whole reason the number lives in a
file whose *name* is the number.
