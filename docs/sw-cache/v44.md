# v44 — JIRA tickets as their own kind in the inbox, which an older cached inboxfilter.js draws as questions (bc-0i27.3)

This is not the v32 pairing. The unstyled-control half is here — v44's `app.js` emits
`class="card jira-card"` and a v43 stylesheet has no rule for it, so the row lays out as
an undivided block of text — but that is the mild half, and it is not what the bump is
for.

The bad pair is the other way round: **v44's `app.js` against v43's `inboxfilter.js`**.
The kind of a row is decided in exactly one place, and the `question` kind's predicate is
"none of the above" — `!q.agent && !q.proposal && !q.delivery && !q.pr && !q.session`
before this release, with `&& !q.jira` added by it. A phone holding the old file therefore
answers `question` for every ticket the new `app.js` puts in the list. What you get is not
an empty section or a missing chip; it is every JIRA ticket assigned to you drawn under
**Questions**, counted in the Questions chip, and — because the kind filter is what the
list is narrowed by — showing up on a screen you narrowed to *the beads asking you
something*. Six tickets would sit among four questions with nothing on the page saying
which was which, and selecting the JIRA chip would show you nothing at all, because the
chip belongs to a table the phone has not got.

That is the exact failure this file exists to prevent: it does not look broken. It looks
like an inbox with ten questions in it. The one word that stops it — `!q.jira` — cannot
help unless the phone has the file that contains it, which is what the version does.
