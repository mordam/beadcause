# v48 — edit mode freezes the screen, against a stylesheet with no way to say so (bc-p49x.1)

The v32 pairing once more, and this time the stale half is worse than a control in the
wrong place: it is a control whose whole job is to *tell you the app has stopped
repainting*, drawn by a stylesheet that has no rule for it.

Edit mode suspends every repaint while it is on. That is deliberate and it is the point —
the element you are pointing at has to still be the element you meant — but a frozen
inbox and a quiet one are the same picture. What separates them is `.editbar`: a fixed
banner across the top, in `--warn`, saying "Edit mode — the screen is frozen", with a
Done beside it. Against a v47 stylesheet that banner has no rule at all, so it is an
unstyled `<div>` appended to the end of `<body>` — below the last card, below the fold,
scrolled past. The freeze still works. Nothing on screen says so, and the way out has
gone with the banner.

The second half of the same pair is `.editmode`, the ✏️ that turns it on. Unstyled it is
not `position: fixed` at all: it lands in the document flow between the ＋ and the toast,
which is off the bottom of the list rather than in the corner beside its peer. So on a
v47 stylesheet the mode is hard to enter and, once entered, invisible and hard to leave —
and a person whose inbox has silently stopped updating reloads the app, which is the one
action that both fixes it and destroys whatever they were in the middle of pointing at.

`/editmode.js` is new in the shell in this version too, so the reverse pair — v47's
`index.html` against v48's file list — is the ordinary additive one: no `#editmode` in
the markup, nothing wires itself to it, and the inbox is the inbox as it was. The freeze
is opt-in from the page's side (`app.js` asks `beadcause.editMode?.frozen?.()` and takes
`false` from a page that never loaded the file), so a half-updated cache cannot freeze a
screen that has no way to unfreeze it.
