# v81 — a v80 page has no `/hashroute.js` tag, and both files that boot on it now call into it (bc-khoe.30.2)

`public/hashroute.js` is new and it is the only thing that knows what the URL hash means.
Two shell files stopped doing their own string work and started asking it, and both ask
**flat** — `window.beadcause.route.parse(...)` in `public/app.js`, `route.viewOfPath(...)`
in `public/viewbar.js` — with no `?.` and no `typeof` guard between them and the answer.
That is deliberate: a notification tap that silently opened nothing would be worse than
one that failed loudly, and the row saying nothing is current is a failure this epic has
already spent a browser check on.

**The pair is a page that predates the script tag.** The only way `hashroute.js` reaches a
document is a `<script src="/hashroute.js">` added to nine `.html` files on this branch,
and six of those are precached. A phone holding v80's `index.html` beside v81's
`app.js` and `viewbar.js` has both callers and none of the callee: `window.beadcause.route`
is `undefined`, and the first thing that touches it throws a `TypeError` out of the IIFE it
is in. For `viewbar.js` that is the whole row — no pills, so no way off the page at all —
and for `app.js` it is `focusHash`, which runs from inside `load()`, so the inbox stops
drawing on the tap of a notification. Neither degrades; both stop.

It is the same shape as v75's `filterpills.js` four versions earlier and the shape bc-nib3.3
went in for — a file added whole to `SHELL` whose only route onto the page is markup a
cached page has not got, called by another file in the same shell. The difference from v75
is which side of the red line it falls on: `filterPills.mount` is `?.`-guarded, so that one
is a control that quietly never appears, and this one is a `TypeError`. `lib/swbump.js`'s
fourth signal reports them differently for exactly that reason.

Everything else on this branch is additive or textual — the grammar module itself,
`test/hashgrammar.mjs`, and four files that read the view table from its new home. The
version is for the tag.

## The number

Written against v75, claimed **v76**, and landing as **v81** — the collision the
[README](README.md) asks for, three times, on three separate downmerges of the same
branch, and the last two are the case the number scheme exists for.

The first downmerge found three notes had landed while this branch sat: bc-me2b took
`v76.md`, bc-rfnr.9.5 took `v77.md`, and bc-khoe.27.1 took `v78.md`. Only the first
surfaced, as an add/add conflict on `docs/sw-cache/v76.md`, because that is the one path
both sides wrote; the landed side kept the number and this note moved to `v79.md`. There
`const CACHE` conflicted **loudly** — this branch held `beadcause-v76` where `main` had
`beadcause-v78` — so the line could not be missed.

The second and third are the quiet ones, and they are the same shape twice. bc-bmry.5 took
`v79.md` and then bc-8t3b took `v80.md`, so each downmerge raised the add/add on the note —
but each time both sides had independently written the *same* `const CACHE` string, and git
merged that line **clean, reporting nothing at all**. Read on its own, `public/sw.js`
looked settled on both occasions. Two unrelated shell changes would have shipped under one
cache key, twice, and no check would have said so. The `const` was opened anyway, on the
standing rule that it is read against the directory rather than against the merge, and set
by hand — to `beadcause-v80` on the second pass and `beadcause-v81` on the third.

That rule is the whole lesson of this note's own history: the loud conflict is the lucky
case and it happened once, the silent one is the ordinary case and it happened twice. The
number lives in a filename because a filename cannot merge silently.

The pair above is stated against **v80**, because that is the shell a phone will actually
be holding. The comparison to `v75`'s `filterpills.js` keeps its number: that is a
reference to a note that landed and kept it, not to this note's own pair.
