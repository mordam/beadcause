# v84 — My Epics is the board alone, and the fold that emptied it is gone (bc-khoe.28)

Home draws every view on top of the same page, and until this version it drew both halves
on all of them: the P0 board above and the card list below, whichever pill was lit. So no
pill showed only its own kind. `public/app.js` now asks `inboxFilter.current()` which pill
is lit and draws one of the two — the board on My Epics, the list on Questions, PRs, Chats
and All Beads — and the board's fold goes with the list it used to reveal, because on a
board-only view a fold is a control whose whole effect is to leave the screen blank.
`public/style.css` follows it: `.p0-kind` loses `min-height: var(--tap)`, `cursor: pointer`
and the button reset, because the heading is an `<h2>` now rather than a `<button>`.

**A v83 stylesheet under a v84 `app.js` is the pair that matters, and it is the heading.**
At v83 `.p0-kind` is written for a control: 44px of tappable height (`--tap`), a pointer
cursor, `-webkit-tap-highlight-color` and `border: 0; background: none` to undo the button
it was. Under the new `app.js` that rule lands on an `<h2>` that does nothing — so the one
line above the board is a thumb-sized target with a pointer over it and a tap highlight
when you press it, and pressing it has no effect at all. That is worse than the old fold
and worse than a plain heading: the phone says there is a control there, twice, and there
is not. Nothing throws, every card still opens, and the failure reads as a fold that has
broken rather than as a stylesheet from before the fold was removed.

The reverse pair — a v84 stylesheet under a v83 `app.js` — is the milder direction and is
still wrong: the fold button is still drawn and still works, but it loses its tap height
and its cursor, so the one line that a shut board leaves on screen becomes an 11px label
you have to know is pressable. Merely older is the direction this repo is happy to leave
alone; this one is a live control that stops looking like one, which is why the pair is
stated in both directions rather than only the first.

## The number

Written against v74, claimed **75**, renamed to 76, renamed again to 79, and landing as
**v84** — renumbered three times. Three branches held 75 when this file was created (the
claim guard named bc-khoe.24 and bc-me2b) and [v75](v75.md) (bc-khoe.24, the scope switch)
merged first, so the first downmerge arrived as the add/add conflict on `v75.md` that this
numbering rule exists to produce. 76 was claimed by a live branch at that moment too, and
the note said so and expected the same conflict again — it came, and it brought two more
with it: [v76](v76.md) went to bc-me2b, [v77](v77.md) to bc-rfnr.9.5 and [v78](v78.md) to
bc-khoe.27.1.

The third move is the one the second one predicted. Five more notes landed on main while
this branch sat — [v79](v79.md) (bc-bmry.5, the approval chip), [v80](v80.md) (bc-8t3b),
[v81](v81.md) (bc-khoe.30.2), [v82](v82.md) (bc-khoe.23) and [v83](v83.md) (bc-khoe.30.3,
the pane shell) — so `v79.md` arrived as the same add/add conflict once more. Main's v79 is
kept verbatim, this note goes to the top of the directory at **84**, and the pair argued
above shifts with it from 78/79 to **83/84**.

The `const` did **not** merge silently on either of the last two downmerges, and both
outcomes stay possible. Each time the two sides held different strings and git raised a
real conflict on the line rather than carrying the stale number through in silence — which
is the loud, easy case. It is still set by hand here, to the highest note in the directory,
because that is the only thing that makes it right in either case.

One other live worktree holds a `v84.md` of its own at the time of writing —
notif-sounds-ka5y153, in the merge queue beside this one — so a fourth rename is as likely
as not. Take the number anyway:
`test/swcache.mjs` forbids a gap as well as a repeat, so dodging upward to a number nobody
has fails the moment this is the branch that lands first. Whichever lands second moves, and
the resolution is the same one again.

The note this builds on is [v74](v74.md) (bc-rfnr.9.7), which took the flat copy of the
board out of the list; this one takes the rest of the list off My Epics and the board off
every other pill. The v75 through v83 above are other beads' work entirely, so a phone on
any of them is not holding half of this.
