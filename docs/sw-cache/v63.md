# v63 — inbox submits go on a queue, and a failed one comes back red (bc-ka5y.10.1, bc-ka5y.10.2)

Answering a card no longer waits for the write. The tap enqueues and returns; a new
`public/submitqueue.js` drains one write at a time behind it. Four files move together:
the new module, `public/index.html` which loads it before `app.js`, `public/app.js`
whose `submit()` now hands the write to it and marks a refused card `q.failed`, and
`public/style.css` which draws that mark — `.failed-note` inside the card and
`.card.has-failed` down its left edge. `public/absorb.js` moves with them, giving each
live flight its own lane at the mark so three queued answers do not stack on one point.

**A v62 shell over a v63 app.js is the pair that matters, and unlike [v62](v62.md) it is
not merely a legibility problem.** A cached v62 shell has no `/submitqueue.js` at all —
it is not in that SHELL list and the fetch handler is network-first, so the page gets it
only if the link is up, which is exactly the condition it exists to survive. app.js is
written for that: `window.beadcause?.submitQueue?.create()` falls back to sending each
write straight out, which is what every build before this one did. So the page answers
questions, one blocking round trip at a time, and the red card still works — `q.failed`
and its stylesheet are both in app.js/style.css, neither is in the module. Degraded, not
broken, and the degradation is precisely the feature.

**A v62 stylesheet under a v63 app.js is the quiet one.** `failedNoteHtml` renders and
its words are readable — it is a `<strong>`, a `<p>` and a button, all of which inherit
something sensible — but with no `.failed-note` rule there is no red border, no tint and
no left edge, so a refused write draws as an unstyled paragraph in the middle of a card.
The sentence still says what happened, which is why this is the lesser half; what it
loses is the thing that makes a red card findable while you are three cards further on,
which is the whole of bc-ka5y.10.2.

**A v62 `absorb.js` under a v63 `app.js` is harmless and worth stating**, because it is
the mixed pair most likely to happen: `slot()` there takes five arguments and ignores a
sixth, so every flight sits in lane 0 and overlapping answers stack on one standoff
point. That is the picture this repo had until now. Nothing throws.

Nothing outside the inbox is touched. `public/sendqueue.js` — the composer queue on the
console and the agents screen — is a different file with different rules and is not
changed here; the two are neighbours, not versions of each other.
