# v92 — `index.html` grows the History pane, and loads `/history.js` to fill it (bc-khoe.30.5)

`public/index.html` had three panes and one of them had contents. It has two empty ones no
longer: the `data-pending` attribute came off `[data-pane="history"]`, the ledger's markup
moved in beside Home's, and the document gained a `<script src="/history.js">` tag to build
it. `public/history.js` itself is not a new file in the cache — it has been in `SHELL`
since the ledger became a tab, because `/history` is a page in its own right — so the
coupling that decides this number runs through that new script tag rather than through JS.

**The pair that needs the bump.** A v91 `index.html` in a phone's cache has no
`<script src="/history.js">` in it, so the container it does not have stays empty and the
History pill stays the `<a href="/history">` that v91's `panes.js` makes it: the app is v91
in full, which is fine. What is **not** fine is a v92 `index.html` beside a v91
`history.js`. The container's list is `id="hist-list"` now, where v91's file asks for
`id="history"` — the ledger would draw into nothing, with no error anywhere and a blank
pane where the record should be. That is a `<script src>` coupling, which is exactly the
shape `test/swbump.mjs` calls advisory-only (bc-nib3.10) because it cannot see it. This
note is the record that it was looked at rather than missed.

**Two other files moved and neither is a pair.**

* `public/hashroute.js` gained decision 5 — a view hash may carry a query,
  `#history?status=closed` — which is purely additive: `parse` answers `query: ''` for every
  hash that has none, and `hashFor(view)` called with no second argument behaves exactly as
  v91's did. A v91 caller beside a v92 grammar sees what it saw.
* `public/app.js`'s ⟳ handler asks `window.beadcause?.panes?.showing?.()` before reloading
  the inbox. Optional all the way down, and `undefined` on every page without panes — so a
  v91 `app.js` beside a v92 shell is v91's ⟳ (it reloads the inbox from whichever pane is
  up, which is the behaviour that was already there), and a v92 `app.js` beside a v91 shell
  is unchanged, because `showing()` answers `'epics'`.

**The one connection is now two mounts, and still one socket.** The History pane registers a
`wake` with `public/panestage.js`, which is what puts that file's standby poll up for the
first time — it was machinery waiting for this bead, and v88's own note says so. `standby:
true` means `public/stream.js` runs it *only* while no ordinary mount is following, and the
pane declares no `want`, so the union stays `presence`: the free park. The pane never
fetches on a wake; it sets a flag and re-reads once, quietly, the next time you look at it.
## The number

Written against **v88**, the highest note in `docs/sw-cache/` when this branch was cut, and
**renumbered three times since**, on the three downmerges this branch has had to sit through.

* **First**, to **v90**: bc-khoe.27.2 landed [v89](v89.md) on `main` while this branch was
  open, so the add/add collision this scheme exists to raise happened on that one path, and
  the file pairs named above moved up with the note. v88 → v90.
* **Second**, to **v91**: bc-khoe.27.3 landed its own [v90](v90.md) — the create form — on
  `main` before this branch could, so the *renumbered* note collided in turn, on the same
  path and for the same reason. v90 → v91. Nothing else in that merge touched this branch's
  files: `main` moved `lib/server.js`, `public/inboxfilter.js`, `public/style.css` and two
  suites this branch has never been near, and the two shell files both sides do share —
  `public/app.js` and `public/index.html` — merged clean, the form's markup landing inside
  `[data-pane="epics"]` where Home's chrome lives and leaving `[data-pane="history"]`
  exactly as this branch left it.
* **Third**, to **v92**: bc-bmry.4 landed [v91](v91.md) — the relay trail — on `main` while
  this branch waited on the queue, a third add/add on the number this note had just moved
  to. v91 → v92. That merge is disjoint from this one everywhere else: `main` brought
  `lib/relayjournal.js`, `lib/strays.js` and `lib/teardown.js` in whole, and its 77 new
  lines in `public/app.js` are the two relay renderers, well away from the thirteen this
  branch changed in the ⟳ handler — so `public/app.js` and `public/index.html` merged clean
  again and `[data-pane="history"]` is untouched by it.

  **The pair sentences above moved up two numbers on this pass, not one.** The second
  renumber moved the filename and left the prose naming a v90 shell against a v89
  `history.js`, a number behind the note it was in; both halves are corrected here, so the
  pair reads as the shell a phone is actually holding — v91 — against the one this note
  ships, v92.

`const CACHE` in `public/sw.js` is set to `beadcause-v92` by hand. **It has now merged
silently on all three passes**, and that is the point of the whole scheme rather than a
footnote to it: on each downmerge this branch and `main` had independently written that line
the same string — `beadcause-v90`, then `beadcause-v91`, then `beadcause-v91` again — so git
reported nothing every time and a phone would have been handed a v92 shell under a v91 key.
The number lives in a filename precisely because a filename cannot merge without a murmur.
`docs/sw-cache/` is what to read it off; the `const` is the half that follows.
