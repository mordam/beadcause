# v80 — a section inside a section, and a v79 stylesheet has no rule for it (bc-8t3b)

`public/monitor.js` gains the `Requested endorsements` subcard: the beads held for
endorsement, drawn under the EpicAdvocate whose work produced them and on the repo's own
card otherwise. The rows it draws are ordinary `.work-row`s and the panel is an ordinary
`.mon-sec`, so nothing here is a new class — with one exception, and it is the whole
reason this pair has a note. For the first time on that page a `.mon-sec` is rendered
*inside another one's* `.mon-body`, and `public/style.css` gains the two rules that say
what a nested section looks like: `.mon-body .mon-sec` (indented, dashed rule) and
`.mon-body .mon-sum` (a shorter, smaller summary line).

**A v79 stylesheet beside a v80 monitor.js is the pair that matters, and what it costs is
legibility rather than function.** Every rule a nested section needs to *work* is already
there at v79 — `.mon-sec`, `.mon-sum`, `.mon-caret`, `.mon-n.warn`, `.mon-body` — so the
subcard opens, closes, and lists its beads exactly as it should. What is missing is the
distinction: without the indent and the dashed rule, an epic's own `Requested
endorsements` panel is drawn at full width with the same solid top border and the same
40px uppercase summary as the sections either side of it. On a card that routinely carries
fourteen epic sections in a row, that is a subcard reading as the next epic along — you
would fold the wrong panel and conclude the epic below has endorsements waiting that it
does not.

The reverse pair — a v80 stylesheet under a v79 `monitor.js` — draws nothing at all: no
v79 page ever nests a `.mon-sec`, so both rules match nothing. That direction is merely
older, which is the direction this repo is happy to leave alone.

## The number

This branch was written against v74 and expected to land as v75. It collided twice, which
is what the [README](README.md)'s renumber procedure is for: bc-khoe.24 took
[v75](v75.md) while the branch was open, and bc-bmry.5 took [v79](v79.md) while the merge
that had renumbered it to v79 was running its tests. Both times the note moved to the next
free number and the `const` in `public/sw.js` was set by hand to match. **It lands as
v80.** Note what the second collision looked like: two branches writing the *same* value
to that `const` merge clean and silently, and only the note's filename was there to
report it — which is exactly why the name is `vNN.md` with no slug.

The pairs above are restated against v79 rather than the v74 they were written against,
because v79 is the shell a phone will actually be holding when this deploys; nothing in
v75 through v79 touches a nested `.mon-sec`, so the argument survived both renumbers
unchanged. The marks this builds on are still [v74](v74.md)'s (bc-rfnr.9.7).

Nothing on the server half of this change forces a bump. `lib/work.js` carries a new
`heldRows` field on each workspace row, and the page is written so that its absence draws
no section at all rather than an empty one — a page cached from a newer deploy against an
older daemon is the case that was designed for, and it is asserted in
`test/heldsubcard.mjs`. What forced the number is the stylesheet, alone.
