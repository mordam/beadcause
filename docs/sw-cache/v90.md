# v90 — an EpicAdvocate becomes a card, and a v89 stylesheet has no rule for its head (bc-henk)

Every advocate on `/monitor` is now a top-level card. `public/monitor.js` stops folding
each EpicAdvocate into a collapsed section of the repo advocate's card (`epicSections`) and
emits an `<article class="… epic-card">` per assigned epic instead (`epicCard`), directly
after the repo card it belongs to. `public/style.css` gains the rules that make that card
work: `.mon-card.epic-card`, and — this is the pair — `.epic-sum`, the button that is
both the card's title and its fold.

**The pair that matters is a v89 `style.css` under a v90 `monitor.js`.** `.epic-sum` is
`.mon-sum` plus an override, and `.mon-sum` is the 12px uppercase strip a *section* header
uses. Without `.epic-sum`, every epic card's name is drawn as a full-width uppercase
section heading, un-clipped, wrapping to two or three lines; the id pill beside it is a
flex item nothing has told to stop shrinking; `.adv-btn` and `.work-graph` in that head go
back to 32px and 36px, so Pause and *Open the epic* are visibly two kinds of control; and
`.mon-card.epic-card` itself has no padding override and no left rule, so the run of cards
loses the one thing tying it to the repo above. Nothing throws. Every press still works.
It is a page that looks like a page, laid out as though somebody had meant it — which is
precisely the failure this number exists for. Measured in Chrome at 393x852: the card is
107px with these rules, which is the difference between a repo with a dozen assigned epics
being 1656px and being a wall.

**The reverse — a v90 `style.css` under a v89 `monitor.js` — is inert.** The old script
draws epic *sections*; every rule above is scoped to `.epic-card` or `.epic-sum` and
matches nothing, so the page is the app exactly as it was.

`public/monitor.html` is untouched: the cards are written into the same `#mon` the roster
has always been written into, so there is no markup half to this at all.

## The number

**v77 was already claimed by another branch when this was written**, and it was taken
anyway. `bc-khoe.10` on `worktree-space-view-khoe10` held a `v77.md` of its own — the
claim register named it at the first write — and the obvious dodge was to take v78 and
leave the number to them. That is wrong here, and test/swcache.mjs is the reason: it fails
the repo for a **gap** in this directory, so a v76 followed by a v78 is a red main until
whichever branch owns v77 lands. A skip is not a cheaper conflict, it is the same conflict
moved onto somebody who has not agreed to it.

It resolved as the ordinary add/add, exactly as [v76](v76.md) describes it happening — and
it resolved against branches this note never named. By the time `main` was merged in,
**v77 had gone to bc-rfnr.9.5 and v78 to bc-khoe.27.1**; `bc-khoe.10`, the branch this note
expected to collide with, had still not landed. So the conflict was on `v77.md` alone,
their note kept the number, and this one moved up past both of them to **v79** — the next
free number in the directory, which is the only rule that survives being wrong about who
you were racing.

The `const` in `public/sw.js` is set **by hand** to the highest note here, and on this
downmerge it did conflict rather than merging in silence, because the two branches had by
then written it different values. That is the lucky direction and it is not the one to
rely on: two branches that pick the *same* number write the `const` the identical string
and git says nothing, which is the whole reason the number lives in a file whose *name* is
the number.

**It happened a second time, and the rule did not change.** This branch stayed open long
enough for `main` to reach **v83**, so the next downmerge hit the same add/add on `v79.md`
— against bc-bmry.5's note this time, which had taken the number while this branch was
still unlanded. Their note kept v79; this one moved to **v84**, again the next free number.
Two renumbers on one branch is not a sign anything went wrong: it is what a directory
numbered by landing order does to a branch that has not landed yet.

**And a third time, which is the one that says what the rule actually is.** The second
renumber picked v84 as the next free number above `main`'s v83 — correctly, at the moment
it was made — and then bc-ka5y.15.3 (#459) merged and *landed* a v84 of its own, three
notification sounds. So this branch's number stopped being the next free one without this
branch changing at all, and `public/sw.js` did not conflict when the two were merged,
because both sides had written `const CACHE = 'beadcause-v84'` the identical string. That
is the silent direction this directory exists to make loud, and the filename is what
reported it. It moved again, to **v86**, and the number below it did not go where anyone expected: two
merge windows spent the evening agreeing which of them held v85, and `main` took it from a
third branch neither was watching — bc-r2b5.2's advocate state on the board card (#497).
v86 is the next free number off `main`, which is the only rule that survives being wrong
about who you were racing, and it is the second time this note has learned that.

The number is therefore correct as of the merge that carries it and not before — it is a
claim about the directory at landing time, which is why `const CACHE` is set by hand and
re-read rather than trusted to a merge.

**A fifth time. The pattern is the point rather than the accident.** v86 went to bc-khoe.28's
board-alone (#430) and v87 to bc-khoe.26's filter pills (#464), each reaching `main` while
this branch was being gated. Five renumbers on one note — v77, v79, v84, v86, v87 — and
**`public/sw.js` merged in silence on three of them**, because the two sides had written
`const CACHE` the identical string and git has nothing to report about a line both branches
agree on. The add/add on this filename was the only thing that spoke, every time. The number is not a thing a branch holds. It is a fact about the
directory at the moment of landing, which is why it is read off `main` immediately before
the push and why the `const` is set by hand and re-read afterwards even when git said
nothing at all.


**A sixth time, and this one moved two numbers rather than one.** `main` reached **v89**
while this branch was gated: v88 went to bc-khoe.30.4's pane stager (#496) and v89 to
bc-khoe.27.2's ＋-starts-an-epic picker (#466), both landing inside the same window. The
add/add was on `v88.md` alone — their note kept it — and this one moved past both to
**v90**, because the rule is the next free number in the directory and not the number
after the one you collided with. Six renumbers now: v77, v79, v84, v86, v87, v88.

The pair above is stated against **v89** rather than the v76 this note was written against,
or the v78, v83, v85, v86, v87 and v88 the earlier renumbers left it at, because v89 is the
shell a phone will be holding by the time this lands. Nothing in the argument changes with any of the
renumbers, and the reason is checkable rather than inferred: `public/style.css` on `main`
carries no rule matching `.epic-card` or `.epic-sum` — those rules arrive with this note and
nowhere else, and none of v84's sounds, v85's board card, v86's board-alone, v87's filter pills,
v88's pane stager or v89's epic picker writes one. Any stylesheet
below this one is therefore missing exactly the rules this note is about, and the mixture it
describes fails the way it describes.
