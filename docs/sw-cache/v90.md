# v90 — ＋ on All Beads opens a create form, and a v89 shell has nowhere to draw it (bc-khoe.27.3)

＋ became a function of the kind in v78: drawn on `My Epics`, `Chats` and `All Beads`,
absent on `Questions` and `PRs`. It did the same thing on all three of the ones that keep
it — start a chat session. This is the first of the two that makes it do the view's own
create: on `All Beads`, ＋ opens a form — title, type, priority, description, acceptance,
parent, labels, and the workspace it lands in — and filing it creates the bead through
`POST /api/bead/create`.

Four files move together. `public/inboxfilter.js`'s `compose` flag stops being a bare
`true` and names what ＋ creates (`chat` or `bead`), with a `creates()` beside `composes()`
that reads it off the lit pill. `public/index.html` gains the `#beadform` sheet.
`public/app.js` branches the ＋ click on `creates()` and gains the form's own state, its
three chip rows and its submit. `public/style.css` gains the handful of rules the form has
that a detail drawer does not.

**The pair to watch is `app.js` and `index.html`, and the branch is guarded on it.** A v90
`app.js` under a v89 document finds no `#beadform` section, so `beadFormEl` is null and the
whole `if (beadFormEl && beadFormFormEl)` block never registers. Left to `creates()` alone,
＋ on `All Beads` would then be a button that does nothing at all — silently, which is worse
than the chat it replaced — so the click tests for the sheet as well as for the answer and
falls back to starting a chat. The other direction is harmless on its own: a v89 `app.js`
under a v90 document never branches on `bead`, never reaches the sheet, and starts a chat
exactly as it did, with an inert `hidden` section sitting in the markup.

**The stylesheet direction is the ordinary one and it is real.** A v90 `app.js` under a v89
`style.css` opens the sheet — `.sheet` has been in the stylesheet since /graph — but
`.beadform-say[hidden] { display: none }` is not there, so the form's own status line is
drawn empty and permanently; `#beadform-ws-field.one .chip` is not there either, so the
single-workspace case reads as a choice you could have made differently; and `.beadform`'s
88dvh is not there, so the form is a 72dvh drawer showing four of its eight fields. None is
fatal and all three are exactly the "a name with no rule behind it" case this scheme exists
for.

**`public/inboxfilter.js` has stopped being a pair, and that is a change since this note was
written.** `creates()` shipped in [v89](v89.md) with bc-khoe.27.2's epic picker, so an older
table is no longer a table missing the function — it is one that answers `chat` for
`All Beads`, because that is what ＋ did there until this branch. All this branch changes in
that file is one word on one row. So a v89 table under a v90 `app.js` says `chat` and starts
one, exactly as v89 does; a v90 table under a v89 `app.js` is asked and says `bead`, and
v89's listener has no branch for that word, so it falls through to the chat as well. Both
directions are the old behaviour — which is the fallback `composes()` has always made, for
the reason it made it: losing the app's primary action to a file that did not load would be
a worse failure than one screen offering the wrong create.

Nothing about `lib/server.js` is cached, so `POST /api/bead/create` is either there or it
is a 404 the form reports on itself.

## The number

Written and claimed against **v78**, the highest note here when this branch was cut, and
landing as **v90** — the collision this scheme exists to raise, three downmerges of one
branch running and eleven notes' worth of it.

* **First downmerge.** bc-bmry.5 took [v79](v79.md), and that was the loud half: an add/add
  on this one path, which git must report. bc-8t3b took [v80](v80.md) and bc-khoe.30.2 took
  [v81](v81.md) without touching this file at all, so those two went by in silence — a
  later number does not conflict with your note. v78 → v82.
* **Second**, after bc-khoe.23's pill counts landed: it had taken [v82](v82.md), loud again
  for the same reason. v82 → v83.
* **Third**, and much the widest: `main` had run on to [v89](v89.md). bc-khoe.30.3 had taken
  [v83](v83.md) — loud — and [v84](v84.md) through [v89](v89.md) passed silently. v83 → v90.

**What the `const` did across the three is the part worth keeping.** On the first two passes
`public/sw.js` merged **clean, reporting nothing**, because this branch and `main` had
independently written that line the *same* string; the filename was the only thing that
raised either collision. On this third pass it did conflict — `beadcause-v83` against
`beadcause-v89` — and only because `main` had got seven notes ahead rather than one. A
conflict on the `const` is luck. `docs/sw-cache/` is what to read the number off, and the
`const` here is set by hand to `beadcause-v90` to match the directory.

The pairs above are restated against **v89** rather than the v78 they were written against,
because v89 is the shell a phone will actually be holding when this deploys. The argument
survives the renumber, though not quite unchanged, and the exception is worth stating rather
than glossing. Checked against `origin/main` rather than assumed: nothing in v79 through v89
puts a `#beadform` section in `public/index.html` or a `.beadform` rule in
`public/style.css`, so a v89 shell has exactly as little to *draw* the form with as a v78
one had, and those two pairs are the pairs they were. The third one is gone — v89 put
`creates()` in `public/inboxfilter.js` for its own create, so that file is no longer new in
this branch and no longer a pair at all.

**The shell moved underneath this note while it waited, and the form moved with it.**
[v83](v83.md) turned `public/index.html` into a pane shell and [v88](v88.md) added
`/panestage.js` to build the panes; on this downmerge the form's markup went inside the
`[data-pane="epics"]` container, which is where Home's own chrome now lives. That is a
placement rather than a pair: the sheet is fixed-position either way, both halves are in the
same precached document, and a pane the shell hides takes the sheet with it — which is what
a sheet belonging to that view wants anyway.
