# v73 — the board is the inbox, and the two marks that say so have no rules at v72 (bc-rfnr.9.7)

The flat list under the board stopped being a second copy of it: with epics owned, the
beads under them are drawn once, in their epic's tree, and what is left underneath is the
things a tree cannot hold — chats, pull requests naming no bead, JIRA tickets, and a
question under nobody's P0 at all. Everything the inbox existed for goes with it, and that
is what this pair is about. `public/app.js` gains three marks: `.pill.p0-asks` on a
collapsed card and `.p0-kind-asks` on the section heading, both saying how many beads under
you are waiting on an answer, and `.p0-answer` inside an expanded bead, which is now the
only route on the phone to the box you answer a question in. `public/style.css` gains
`.p0-kind-asks`, `.p0-answer`, `.p0-card.asks` and a widened `.p0-head .pill`.

**A v72 stylesheet beside a v73 app.js is the pair that matters, and the answer control is
the half that hurts.** `.p0-answer` is a bare `<button>` at v72 — system font, grey face,
beveled on four sides, shrink-to-fit — sitting on the `.p0-bead-acts` row beside a graph
link that is a properly drawn 40px pill. It still works; it reads as a browser default that
escaped a stylesheet, which on the one control that answers a question is the worst place
on the page for that. `.p0-kind-asks` is worse in a quieter way: with no rule it inherits
the heading's own `text-transform: uppercase` and 0.08em tracking, so "1 asks you" is
printed as a tracked-out capitalised label beside the section name and reads as part of the
heading rather than as a count of what is waiting. `.p0-head .pill` at v72 is still
`.p0-head .pill.id`, so the new pill flexes and stretches across the gap to the counts,
which turns a card's head line into a bar.

`.p0-card.asks` is the one that would merely be missing: a leading edge 3px rather than
5px, which is a mark you do not notice rather than a mark drawn wrong.

Nothing throws and every tap works. That is the point — it looks like a rendering fault in
the section it is drawn in, which is exactly the failure this version number exists to
prevent.

## The number

This branch was written against v67 and is landing as **v73**, which is what the paragraph
it replaced said would happen: the downmerge takes the next free number rather than the one
the branch was written for, because a second document under a number `main` has already
spent would make the cache history ambiguous about which shell a given version names, and
the number's only job is to be unambiguous. This is the sixth number this note has carried.
Six landed while it was open — [v67](v67.md) to the top bar (bc-khoe.5), [v68](v68.md) to
the warm store (bc-1kwl.14), [v69](v69.md) to the pill row and the app shell (bc-khoe.1),
[v70](v70.md) to starting an epic from the board (bc-s8mc), [v71](v71.md) to the epic grid
and its full-tab card (bc-grut) and [v72](v72.md) to an epic rooting work at any priority
(bc-htoy) — and four of the six collided on the path, exactly the way the
[README](README.md) intends: an add/add conflict on `v67.md`, then on `v69.md`, then on
`v70.md`, then on `v71.md`. Only the first of those left the `const` in `public/sw.js`
merging as an ordinary content conflict that either side could have won silently; every
collision since has had to be settled in the note, which is the file that carries the
number. The bead this builds on is [v66](v66.md) (bc-rfnr.9.4), and the pair above is
stated against v72 because that is the shell a phone will actually be holding.

The reverse pair — a v73 stylesheet under a v72 `app.js` — draws nothing at all, because no
v72 page emits any of these classes, and the list under the board is the list it has always
been. That direction is merely older, which is the direction this repo is happy to leave
alone.
