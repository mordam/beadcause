# v96 — `/history` stops being a document, so the shell stops precaching it (bc-khoe.30.7)

The ledger became a pane of the shell in v92 (bc-khoe.30.5) and `/history` went on being a
document beside it, because home screens hold that address and `/closed` redirects to it.
This is the branch that lands those addresses on the pane: `lib/server.js` answers
`/history` and `/history.html` with a **302 to `/#history`**, and `/closed` and `/done`
with a 302 to `/#history?status=closed`.

A path the daemon answers with a 302 cannot be in `SHELL` — `Cache.put` refuses a
redirected response and `install` is one all-or-nothing `addAll`, so one of them left in
the list would leave *nothing* cached on every installed phone for as long as that worker
lived. So `/history` and `/history.html` come out. `/history.js` stays, because the pane is
drawn with it.

## Why this one owes a bump, which is not the usual argument

The usual test is whether the change leaves a **broken** pair rather than a merely older
one, and by that test this change is safe in every direction:

- **A v95 shell against this daemon.** `/history` is requested, the daemon answers 302, the
  fetch follows it to `/`, and the shell opens on `#history`. `fetchAndStore` refuses to
  store a redirected response, so nothing is poisoned. Correct, first try, on a phone that
  has not updated at all.
- **A v95 shell, offline.** `/history` hits the entry cached under that name — the old
  `history.html` document, which `public/history.js` still knows how to draw, because
  bc-khoe.30.5 built it to run in either. Older, not broken.
- **This shell against an older daemon**, which is only a window of seconds during a
  deploy: `/history` is served as the document it still is, from the network, and the pane
  is never reached. Also the app as it was.

What makes the bump owed is the other thing `activate` does. It deletes every cache whose
key is not the current one — and nothing else ever removes a single entry. `install`
re-fetches everything in `SHELL` into whatever cache `CACHE` names, so a changed `sw.js`
under an unchanged version would add the new list *on top of* the old one, and the two
entries this branch removed would sit there for the life of the app. The exact match at the
top of `fallback` would go on answering them with the v95 document, `VIEW_HOPS` would never
be consulted, and the half of this change that is about being offline would never happen on
any phone that already has the app — which is every phone. The bump is what makes a
**removal** from `SHELL` mean anything at all.

That is worth stating separately because it does not follow from the mixed-pair rule at
all: the rule is about files that disagree, and this is about an entry nobody wanted that
nothing else can evict.

## What else moved in this worker

`VIEW_HOPS` and `viewAddress`, and one step added to `fallback` between the `ignoreSearch`
retry and the fall to `/`: a request whose path names a view is answered with
`Response.redirect` to that view's hash rather than with the index page. Without it, an
offline phone opening the `/history` shortcut misses the cache twice and is served the
shell **at `/history` with an empty hash** — Home, whatever was tapped, which is the
acceptance criterion of this change failing in the one place nobody looks.

It is deliberately *below* the two cache lookups, and that is what makes it safe as the
rest of the epic lands. `/monitor` and its eight siblings, and `/releases` and its two, are
still documents, still aliases rather than hops, and still in `SHELL` — so the exact match
answers them long before this table is reached. A path only ever gets here once it has left
the shell, which is the same commit that makes it a redirect. The two lists are held
against each other by `test/pagealias.mjs` rather than by anybody remembering.

`/closed` and `/done` gain something they never had: they are still not in `SHELL` and
still cannot be, but the answer to them is now knowable here, because the far end of the
hop is a fragment of a document this worker already holds rather than a page only the
daemon can name. The note in `sw.js` that said resolving them meant knowing a redirect only
the daemon has is updated rather than deleted — it was true when it was written, and what
changed is the ledger, not the reasoning.
